# 품질·파싱·공문서 생성 개선 검증 (2026-09-30)

기준은 `2065b45`(v4.17.1)이다. `origin/main`을 ff-only로 갱신한 뒤 독립 worktree에서 수정했다. 기존 코퍼스, 정답, 평가기, 표본 제외 규칙은 바꾸지 않았다.

집계 수치·개별 회귀 비교·평가기 해시는 [검증 JSON](quality-improvements-2026-09-30.json)와 [단독 성능 JSON](quality-performance-2026-09-30.json)에 함께 보존한다.

## 판정 방법

품질 비율은 99% 이상을 목표로 한다. CER·phantom처럼 낮을수록 좋은 오류율은 1% 이하, 파싱 오류·퍼즈 사고는 0건을 목표로 한다. 시간은 동일 입력 A/B의 중앙값으로 비교하며 품질 점수로 환산하지 않는다. 기존 게이트 통과와 모든 지표 99% 달성은 별개이다.

## 구현

- 표 위 무괘선 단위 줄을 별도 문단으로 복원하고, 얇은 가상 빈 띠가 같은 획을 두 테두리로 세지 않도록 했다. 실제 변·그림·중첩표·다른 제작기 클립 표의 머리행은 보존한다.
- 긴 셀 안 조문 밑줄과 행 괘선을 글자·패딩·세로 경계로 구별한다. 반복 머리글 뒤의 쪽넘김 행은 기존 문장·좌표 검증을 재사용한다. 표시 태그는 조문 번호 판정·첫 글자 폭·균등배분 비율에서 제외하고 출력에는 보존한다.
- 큰 표의 글자 배정 후보를 세로 구간으로 줄이고, 글줄 정렬을 재사용한다. 병합 셀과 동률 우선순위는 유지한다.
- 공문서 인라인 서식·링크 표시 글자를 출력과 같은 파서로 폭 계산하고, 금칙 문자 앞의 이모지를 쪼개지 않는다. 문단 내 반복 조판 계산을 재사용한다.

## 검증

최종 PDF 1,911문서의 전체 coverage 게이트는 99.774%로 통과했다. 채점 대상 1,729·OCR 별도 114·weak 68·tiny 68이다. 문서별 coverage 게이트보다 낮은 91건은 평가기에 그대로 남아 있으므로 전 문서 만점이라는 의미는 아니다.

HWPX 2,286문서·정답 5,548,157자: 글자 recall·순서 100%, 표 완전 일치 99.6351%, 셀 F1 99.7668%, 셀 완전 일치 99.9588%, 내용 NED 99.9545%. HWP5↔HWPX 1,120쌍·표 4,249개는 모든 쌍 품질 게이트 100%·오류 0이다. 이 경로의 소스는 수정하지 않았고 전체 `score.mjs`로 검증했다.

DOCX 36·XLSX 28·XLS 15·HWPML 9·큰 시트 8건: 문자·숫자 recall 100%, 파싱 오류 0. 왕복 변환의 양방향 글자 회수·표·셀 일치 100%, 제목·수식·글줄·생성 오류 0이다. 리플로·페이지·비식별 게이트도 통과했다.

최종 소스 독립 검증: `npm run typecheck`, `npm test` 2,745/2,745(실패·취소·skip·todo 0), ESM/CJS/DTS 빌드, `git diff --check` 통과. 테스트는 실패 재현 후 수정했다. 원본 worktree와 고정 finalG 소스 11개 및 package/config의 바이트 동일성을 확인했다.

한컴 실렌더 시각 오라클은 macOS 한컴 앱이 설치되어 있지 않아 실행하지 못했다. 따라서 실제 한컴 화면에서의 검증을 통과했다고 주장하지 않는다.

태그 배치·u/취소선·날짜·기호 54조합에서 기존 평문 정규화와 출력 태그 순서가 유지됨을 별도 검증했다.

기하 테스트는 첫 글자에 열린 밑줄·취소선 태그가 붙어도 원래 글리프 폭을 쓰며, 출력 서식을 보존하는지 확인한다. 실제 문서의 `<u>품`(14pt/1자), `<u>기업`(28pt/2자)처럼 태그가 붙으면 글자 수를 부풀리던 사례를 다룬다.

## 성능 측정

`bench/perf-quality.mjs`는 기준 checkout과 변경 checkout을 같은 프로세스에서 비교한다. 문단 맞춤 768조합, 500/2,500/5,000칸의 배정 결과, 200문단 공문서 생성 ZIP 엔트리를 먼저 동등성 검사한다. 조판 1,000회는 7회·칸 배정은 5회 중앙값, 생성 API는 순서를 번갈아 9회 실행하고 첫 2회를 제외한 중앙값이다. 추가 `--pdf=/문서.pdf` 옵션은 파일 읽기를 제외한 전체 PDF API를 같은 옵션으로 9회 교대 실행한다. PDF.js의 호출별 임시 문서 ID(`g_d0_f1`→`g_d1_f1`) 접두사만 접은 IR과 바이트 동일 Markdown을 먼저 확인하고 첫 2회를 제외한 중앙값을 비교한다. 대표 입력은 ODL 125(짧은 글), 188(140셀 표), 189(3개 표·133셀)이다. OCR은 끄고 images는 true이다. 전수 PDF/OCR 시간은 병렬 검증 경합의 영향을 받아 속도 개선 근거로 사용하지 않는다.

검증 환경: Node v26.10.0 / darwin arm64 / Apple M4. 전수 벤치·퍼즈 종료 후 단독 측정했다.

## 재현

기준 checkout(`2065b45`)과 변경 checkout에 같은 코퍼스·OCR 캐시를 연결하고 각각 빌드한다.

```sh
npm run typecheck
npm test
npm run build
npm run bench:gate
node bench/gen-sweep.mjs bench/out/gen-after.json
node bench/gen-repro.mjs --verbose
node bench/perf-quality.mjs --baseline=/절대경로/기준checkout --pdf=/절대경로/대표문서.pdf
```

단독 퍼즈는 전체 5,910파일×4변형 + 생성 왕복 60건 = 23,700런이며, 최종 소스로 통과했다. crash·hang·noCode·slow·genInvalid 모두 0건이다. 최종 검증에서는 게이트를 단계별로 실행하고, 변경된 PDF 경로는 최종 스냅샷으로 재측정한다. 성능 측정은 다른 벤치·테스트 종료 후 실행한다. 원본 ODL은 원본 evaluator를 기본 및 `plain + HTML` 출력에 각각 적용한다.

## 정규화의 한계

텍스트 벤치 정답은 원본 HWPX/DOCX의 파싱·정규화 결과이다. 편람 등록번호의 실제 HWPX XML에는 `정 보 공 개 과` / ` - ` / `135`의 분산 공백이 있다. `정보공개과-135`는 정규화 GT이며 원문 XML 그대로가 아니다. 이번 수정은 기존 균등배분 정책이 표시 태그 유무에 따라 달라지지 않게 한다. 공백을 없애는 것이 모든 원문에서 옳다는 새 정책을 도입하지 않았다.

## 남은 목표

현재 99% 미달 항목은 PDF 표 완전 일치 97.9408%·셀 완전 일치 98.5981%·내용 NED 98.2072%, 중첩표 완전 일치 93.0693%, 공백 F1 약 98.8%, 별표 PDF 완전 일치 96.821%·수식 회수 7/11, ODL 총점 96.0144/97.1601, OCR 표 및 공문서 서식 재현이다. 이미 99%·100%인 지표는 유지했다.

모든 지표 99%를 달성하려면 OCR 표 복원, 문서 계층·차트 영역 해석, 공문서 원본의 문단별 스타일 정보 보존을 추가로 다뤄야 한다. Markdown 입력에는 원본의 개별 글꼴·정렬·줄간격 정보가 없는 경우가 있어 원본 서식의 완전한 재현이 제한된다. 점수를 올리기 위해 정답·평가기·제외 규칙을 수정하지 않았다.
